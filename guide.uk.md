# Pixel 5 (redfin): посібник зі збирання, пакування та прошивання KernelSU-Next + SuSFS

[English](guide.md) | [Українська](guide.uk.md)

Це відтворюваний робочий процес для ядра Android 14 Pixel 5 (`redfin`) у цьому репозиторії. Він збирає KernelSU-Next із підтримкою legacy SuSFS v2, зберігаючи сумісність зі стоковими модулями ядра з `/vendor`.

Скрипти готують дерево вихідних текстів і створюють образи. Вони **не** прошивають телефон. Самостійно запускайте команди збирання та пакування: обидві можуть тривати довго.

## Область застосування та припущення

- Пристрій: Google Pixel 5 (`redfin`).
- Стоковий реліз для цього проєкту: Android 14 `UP1A.231105.001.B2`.
- Гілка ядра: `android-msm-redbull-4.19-android14`.
- Обов'язковий коміт бази ядра: `7b0944645172e8b690d42f68c8973ccb0ca45730`.
- Конфігурація ядра: `private/msm-google/build.config.redbull.vintf`.
- Хост збірки: WSL/Linux.
- Завантажувач: розблокований.

Не використовуйте `build_redbull.sh` для цього проєкту. Він обирає іншу конфігурацію і не є шляхом VINTF/KMI-сумісної збірки, що використовується тут.

## Структура репозиторію

| Шлях | Призначення |
| --- | --- |
| `build_ksu_next_susfs_kmi.sh` | Скидає вихідні тексти до закріпленої бази, застосовує серію патчів, збирає ядро та записує доказ збірки. Не пакує та не прошиває. |
| `package_kernel_images.sh` | Пакує вже зібране ядро в `boot.img` та `vendor_boot.img`. Не збирає та не прошиває. |
| `patches/` | Упорядковані патчі, придатні до перевірки: KernelSU-Next, SuSFS, ручні хуки, KMI та конфігурація. |
| `patches/series` | Авторитетний порядок серії патчів. |
| `config/versions.env` | Закріплені база ядра Google і ревізія KernelSU-Next. |
| `tools/verify_stock_vendor_module_abi.sh` | Внутрішня перевірка ABI зі стоковими модулями vendor. |
| `out/android-msm-pixel-4.19/dist/` | Результат збірки, доказ, ABI-звіт і фінальні артефакти ядра. Не відстежується Git. |
| `stock-images/` | Відповідні заводські `boot.img`, `vendor_boot.img` та `vendor.img`. Не відстежується Git. |
| `repacked-images/` | Пакети образів, створені скриптом пакування. Не відстежується Git. |

KernelSU-Next і SuSFS навмисно є окремими патчами. Це робить оновлення придатними до перевірки та не дозволяє оновленню KernelSU непомітно змінити код SuSFS.

## 1. Передумови

Встановіть залежності збірки ядра Android, `repo`, Git, Python 3, `lz4`, `cpio`, `unpack_bootimg`, `mkbootimg`, `avbtool`, `fastboot` та `adb`. Точне розташування інструментів можна вказати через змінні середовища, якщо їх немає в `PATH`.

Для перевірки root після прошивання та керування дозволами встановіть APK
KernelSU-Next Manager, сумісний із вбудованим компонентом KernelSU-Next.

Тримайте доступними такі файли заводського образу для цільового релізу:

- `boot.img`
- `vendor_boot.img`
- `vendor.img`
- `vbmeta.img`
- `vbmeta_system.img`

Використовуйте файли, витягнуті з того самого factory image, який встановлений на телефоні. Не поєднуйте образи boot або vbmeta з іншої збірки. Перед першою прошивкою збережіть копію відомих робочих стокових образів поза цим репозиторієм — це шлях відновлення.

## 2. Оберіть каталоги та відкрийте checkout у WSL

GitHub-репозиторій проєкту та checkout Google `repo` є окремими. Файли
проєкту мають бути доступні всередині checkout ядра, оскільки скрипт збірки
використовує поточний каталог як корінь checkout. Оберіть шляхи для своєї
системи та залиште змінні в тій самій сесії shell:

```bash
KERNEL_CHECKOUT="$HOME/dev/redbull-kernel"
PROJECT_DIR="$KERNEL_CHECKOUT/ksun-susfs"
STOCK_IMAGES_DIR="$KERNEL_CHECKOUT/stock-images"
cd "$KERNEL_CHECKOUT"
```

Це приклади розташування, а не фіксовані вимоги. `PROJECT_DIR` може бути
будь-яким каталогом із цим GitHub-репозиторієм, але кожну команду збирання та
пакування потрібно запускати, коли поточним є корінь checkout ядра.

## 3. Отримайте або повторно використайте дерево вихідних текстів Google

Для нового checkout ініціалізуйте й синхронізуйте маніфест ядра Google, а
потім клонуйте цей проєкт у вибраний `PROJECT_DIR`:

```bash
mkdir -p "$KERNEL_CHECKOUT"
cd "$KERNEL_CHECKOUT"
repo init -u https://android.googlesource.com/kernel/manifest \
  -b android-msm-redbull-4.19-android14
repo sync -j8
git clone https://github.com/osidius-the-emphatic/redfin-ksun-susfs.git "$PROJECT_DIR"
```

Для цих команд не існує обов'язкового формату прогресу. Успішні `repo init`,
`repo sync` і `git clone` завершуються зі статусом `0`; будь-яка критична
помилка або ненульовий статус означає, що checkout неповний і його потрібно
виправити до початку збірки.

Якщо checkout ядра та репозиторій проєкту вже існують, не повторюйте ці
команди. Переконайтеся, що наявні `private/msm-google`, `build` і
`$PROJECT_DIR/patches/series`, після чого переходьте до розділу 4.

### Повторна збірка з наявним checkout

Після попередньої спроби локально поверніть проєкти Google `repo` до ревізій
маніфесту перед повторним застосуванням серії патчів:

```bash
cd "$KERNEL_CHECKOUT"
repo forall -c 'git reset --hard && git clean -fd'
repo sync -l -d
```

У разі успіху ці команди завершуються зі статусом `0`. Після цього проєкти
Google чисті та перебувають на ревізіях маніфесту; команда може виводити
прогрес, але єдиного обов'язкового фінального рядка немає. Ненульовий статус
означає, що reset або локальна синхронізація не завершилися.

Це видаляє відстежувані та невідстежувані зміни всередині проєктів `repo`,
включно з попередньою локальною інтеграцією KernelSU/SuSFS. Об'єкти повторно
не завантажуються: `repo sync -l -d` використовує вже наявні локальні об'єкти.
Якщо локальних об'єктів недостатньо, один раз виконайте звичайний `repo sync`.

Не запускайте reset-команди, якщо потрібно зберегти локальні зміни ядра.
Натомість використайте окремий checkout або спочатку збережіть ці зміни.
Скрипт збірки вимагає, щоб проєкт ядра Google точно перебував на закріпленому
базовому коміті, і відмовляється працювати з відстежуваними змінами.

Коли потрібна чиста повторна збірка, видаліть згенерований результат:

```bash
rm -rf "$KERNEL_CHECKOUT/out/android-msm-pixel-4.19"
```

`out/` — це згенерований результат. Видаляйте лише цей точний каталог після
підтвердження, що `KERNEL_CHECKOUT` є потрібним checkout ядра.

## 4. Розмістіть стокові образи

Створіть каталог, названий у `STOCK_IMAGES_DIR`, і скопіюйте до нього
відповідні заводські `boot.img`, `vendor_boot.img`, `vendor.img`, `vbmeta.img`
та `vbmeta_system.img`. Та сама змінна передається обом скриптам. Скрипти
автоматично знаходять інструменти образів Android усередині checkout; не
потрібно експортувати `MKBOOTIMG`, `UNPACK_BOOTIMG` чи `AVBTOOL`.

Перед початком довгої збірки перевірте вхідні дані:

```bash
test -f "$STOCK_IMAGES_DIR/boot.img"
test -f "$STOCK_IMAGES_DIR/vendor_boot.img"
test -f "$STOCK_IMAGES_DIR/vendor.img"
test -f "$STOCK_IMAGES_DIR/vbmeta.img"
test -f "$STOCK_IMAGES_DIR/vbmeta_system.img"
command -v lz4
command -v cpio
```

Очікуваний результат:

- Кожна команда `test -f` нічого не виводить і повертає статус `0`, якщо файл існує. Відсутній файл дає статус `1`; зупиніться та виправте шлях.
- Кожна команда `command -v` виводить шлях до виконуваного файла (наприклад, `/usr/bin/lz4`) і повертає статус `0`. Якщо нічого не виведено або статус ненульовий, встановіть відсутній інструмент чи додайте його до `PATH`.

Під час ручної перевірки одразу після команди виконайте `echo $?`, щоб
переглянути її статус. Не переходьте до збірки, доки всі сім перевірок не
завершаться успішно.

## 5. Зберіть KernelSU-Next + SuSFS

Це тривалий крок. Скрипт скидає `private/msm-google` до коміту, закріпленого в `config/versions.env`, переходить на закріплену ревізію KernelSU-Next, застосовує впорядковані патчі, збирає з VINTF-конфігурацією та записує докази до `dist/`.

Підсумковий release ядра має вигляд `4.19.278-ksun-susfs-g<integration-sha>`, де SHA ідентифікує єдиний локальний коміт із застосованою інтеграцією. Він навмисно не використовує неінформативний суфікс Git-відстані `00001`.

```bash
cd "$KERNEL_CHECKOUT"
bash "$PROJECT_DIR/build_ksu_next_susfs_kmi.sh" \
  --stock-images-dir "$STOCK_IMAGES_DIR"
```

Не запускайте пакування, доки ця команда не завершиться успішно.

Успішний вивід має містити:

- незмінний SHA-256 `seccomp.h` до та після збірки;
- запис `kernel_release=4.19.278-ksun-susfs-g<integration-sha>` у доказі;
- увімкнені перевірки конфігурації KernelSU і SuSFS;
- SHA-256 хеші для `Image.lz4-dtb` та `vmlinux`;
- ABI-звіт з нулем CRC-розбіжностей і нулем відсутніх символів.

Ключові вихідні файли:

```text
out/android-msm-pixel-4.19/dist/ksu-next-susfs-build-proof.txt
out/android-msm-pixel-4.19/dist/stock-vendor-module-abi-kmi-full-report.txt
```

Будь-яка ABI-розбіжність або відсутній символ означає невдалу збірку для стокового `vendor.img`: не пакуйте й не прошивайте її. Патчі KMI зберігають CRC, необхідні стоковим модулям vendor, без вилучення SuSFS.

## 6. Перевірте результат збірки

Перед пакуванням безпосередньо перегляньте доказ та результат ABI:

```bash
cd "$KERNEL_CHECKOUT"
sed -n '1,240p' out/android-msm-pixel-4.19/dist/ksu-next-susfs-build-proof.txt
sed -n '1,260p' out/android-msm-pixel-4.19/dist/stock-vendor-module-abi-kmi-full-report.txt
test -s out/android-msm-pixel-4.19/dist/Image.lz4-dtb
```

Ці файли — машинозчитувані докази, а не додаткові вхідні дані наступної команди. Успішна збірка завершується зі статусом 0, створює обидва файли та виводить їхні шляхи. У доказі `seccomp_stock_sha256` і `seccomp_post_build_sha256` мають бути ідентичними, хеші образів — наявними, а перевірки конфігурації KernelSU/SuSFS — успішними. В ABI-звіті обов'язкові `crc_mismatches=0` і `missing_kernel_symbols=0`; значення `checked_vendor_modules` має бути додатним (111 для зазначеного стокового образу). Будь-яка ненульова розбіжність, відсутній файл або ненульовий код завершення команди означає зупинитися: не пакуйте й не прошивайте.

`sed` лише виводить докази; він нічого не змінює. `test -s` нічого не виводить і повертає 0, коли образ ядра існує та не порожній; відсутній або порожній образ повертає 1. Доказ фіксує точний коміт вихідних текстів KernelSU, перевірки цілісності `seccomp`, контрольну суму фінальної конфігурації та хеші образів. Серія патчів фіксується окремо в `patches/series`.

## 7. Запакуйте boot і vendor_boot

Пакування відокремлене від збирання. Воно використовує успішний `dist/Image.lz4-dtb` і стокові артефакти boot, а потім записує новий каталог нижче `repacked-images/`.

```bash
cd "$KERNEL_CHECKOUT"
bash "$PROJECT_DIR/package_kernel_images.sh" \
  --stock-images-dir "$STOCK_IMAGES_DIR"
```

Скрипт виводить точний каталог результату. Перевірте його перед прошиванням: він має містити замінні `boot.img`, `vendor_boot.img`, контрольні суми, доказ та метадані пакування.

Зазвичай немає потреби підтримувати окремі шляхи стокових образів: єдина змінна `STOCK_IMAGES_DIR` передається обом скриптам. Значення скриптів за замовчуванням `./stock-images` зберігається лише як запасний варіант для прямого використання без змінної.

Ніколи не перезаписуйте стокові вхідні образи. Згенеровані образи належать до `repacked-images/`; стокові вхідні дані лишаються незмінними артефактами відновлення.

## 8. Прошийте згенеровані образи

Прошивання змінює пристрій. Підтвердьте каталог результату та хеші, а потім перезавантажтеся до bootloader:

```bash
adb reboot bootloader
fastboot devices
fastboot getvar current-slot
```

Зафіксуйте показаний слот (`a` або `b`). Це цільовий слот для нового ядра. На
A/B-пристрої прошивання `boot` або `vendor_boot` без явного слоту записує до
поточного слоту; інший слот зберігає попередній вміст і залишається доступним
як fallback. Якщо новий слот не завантажиться і не буде позначений успішним,
bootloader може автоматично спробувати інший слот. Також можна перемкнутися
вручну через `fastboot set_active a` або `fastboot set_active b`.

Використайте згенеровані `boot.img` і `vendor_boot.img` з пакета разом із
відповідними заводськими `vbmeta.img` та `vbmeta_system.img` з
`STOCK_IMAGES_DIR`. Усталений протокол Pixel 5 прошиває обидва розділи vbmeta
в обидва слоти й вимикає AVB-перевірку та verity:

```bash
PACKAGE_DIR="$KERNEL_CHECKOUT/repacked-images/redbull.xxxxxx"  # use the directory printed by packaging
fastboot flash boot "$PACKAGE_DIR/boot.img"
fastboot flash vendor_boot "$PACKAGE_DIR/vendor_boot.img"
fastboot flash --slot all --disable-verity --disable-verification vbmeta "$STOCK_IMAGES_DIR/vbmeta.img"
fastboot flash --slot all --disable-verity --disable-verification vbmeta_system "$STOCK_IMAGES_DIR/vbmeta_system.img"
fastboot reboot
```

`PACKAGE_DIR` запобігає випадковому прошиванню стокового образу або старішого пакета. Замініть `redbull.xxxxxx` на фактичну назву каталогу; не вводьте заповнювач буквально. `--slot all` застосовується лише до `vbmeta` та `vbmeta_system`; згенеровані boot-образи прошиваються лише до поточного слоту.

`--disable-verity` та `--disable-verification` свідомо змінюють стан AVB.
Використовуйте лише відповідні заводські `vbmeta.img` та `vbmeta_system.img`
для встановленого релізу. Не прошивайте `vendor.img`; цей робочий процес не
змінює стоковий розділ vendor.

Зміна стану AVB може вплинути на доступ до зашифрованих даних користувача.
Зробіть актуальну резервну копію перед прошиванням і будьте готові до вимоги
Android очистити `data`, якщо пристрій не зможе перевірити або розблокувати
наявні дані. У цьому проєкті попередній тест із неповним протоколом vbmeta
потребував скидання, але це не було контрольованим доказом, що причиною були
саме прапорці `--disable-*`.

Також не встановлено, чи потрібно прошивати `vbmeta.img` та
`vbmeta_system.img` з цими прапорцями під час кожного наступного оновлення
ядра, чи достатньо зробити це один раз. Прапорці записуються в стан vbmeta під
час операції прошивання vbmeta; прошивання нового `boot` або `vendor_boot` саме
по собі цей стан не перезаписує. Однак взаємодія саме Pixel 5 із зашифрованими
даними та TEE недостатньо задокументована, щоб довести, що оновлення лише
boot/vendor_boot завжди безпечне. Поки це не перевірено на цьому пристрої без
втрати даних, вважайте повний протокол із чотирма образами вище безпечним
значенням за замовчуванням. Контрольний подальший тест може прошити лише
boot/vendor_boot в інший слот, перевірити доступність `/data`, а потім
встановити, чи надійна коротша процедура; не робіть такого висновку з одного
успішного завантаження.

## 9. Перевірте завантажене ядро

Спочатку підтвердьте, що телефон завантажився, та визначте запущене ядро.
Ці команди не потребують root:

```bash
adb wait-for-device
adb shell uname -r
```

Результат `uname -r` має дорівнювати значенню
`4.19.278-ksun-susfs-g<integration-sha>`, записаному в доказі збірки. Якщо
телефон доступний, але повідомляє інший release, зупиніться: завантажилося
інше ядро.

Драйвер KernelSU-Next вбудований у ядро, але Manager є окремим Android-
застосунком. Root не надається ADB shell автоматично. Відкрийте встановлений KernelSU-Next
Manager, перейдіть до його загальних налаштувань і явно увімкніть root-доступ
для ADB/shell (точна назва може відрізнятися залежно від версії Manager).
Лише після цього виконайте перевірку root:

```bash
adb shell su -c id
```

Результат має містити `uid=0(root)` і зазвичай SELinux-контекст KernelSU,
наприклад `u:r:ksu:s0`. Якщо Manager не надав root для ADB/shell, команда
завершиться помилкою або поверне non-root identity; це результат налаштування
дозволів, а не доказ того, що ядро не завантажилося.

Наступна перевірка списку модулів зазвичай працює без root, а читання журналу
ядра потребує підтвердженого вище root-доступу:

```bash
adb shell 'grep "^incrementalfs " /proc/modules'
adb shell su -c 'dmesg | grep -Ei "incrementalfs|disagrees about version|invalid module format"'
```

Наявність `incrementalfs` у `/proc/modules` без повідомлень `disagrees about version` або `invalid module format` є перевіркою під час виконання, що відповідає ABI-аудиту.

Не всі збірки KernelSU надають `/proc/ksu/version` або `/proc/ksu/susfs_enabled_features`. Лише їхня відсутність не є помилкою. Перевіряйте через `su`, менеджер KernelSU-Next та доказ збірки.

## 10. Відновлення

Якщо пристрій не завантажується, поверніться до bootloader та відновіть відомі робочі стокові `boot.img` і `vendor_boot.img` для встановленого factory release:

```bash
fastboot flash boot "$STOCK_IMAGES_DIR/boot.img"
fastboot flash vendor_boot "$STOCK_IMAGES_DIR/vendor_boot.img"
fastboot reboot
```

Для пристрою A/B спочатку перевірте активний слот через `fastboot getvar current-slot`. Не перемикайте та не перезаписуйте слоти необережно; якщо відновлення потрібне для обох слотів, використовуйте процедуру factory image.

## Оновлення KernelSU-Next або SuSFS

Не редагуйте згенеровані вихідні файли та не замінюйте цілі дерева вихідних текстів архівами. Оновлюйте відповідну закріплену ревізію та її власний набір патчів:

1. Змініть ref і коміт KernelSU-Next у `config/versions.env`.
2. Оновіть лише специфічні для KernelSU-Next патчі, включно з виключенням backport seccomp, якщо воно досі застосовне.
3. Окремо оновіть специфічні для SuSFS патчі, коли змінюється версія SuSFS.
4. Перебазуйте патчі інтеграції, KMI та конфігурації в порядку `patches/series`.
5. Перевірте серію через `git apply --check` або перевірки підготовки скрипта збірки.
6. Виконайте чисту збірку та вимагайте ABI-звіт модулів vendor без розбіжностей до пакування.

Менеджер і вбудований компонент KernelSU пов'язані, але можуть не показувати ідентичні числові версії. Доказ фіксує точний коміт KernelSU; використовуйте цей коміт, а не лише показаний номер версії, під час порівняння збірок.

## Навіщо існує `versions.env`

`config/versions.env` — єдине джерело істини щодо upstream-вхідних даних: коміту бази ядра Google та пари тег/коміт KernelSU-Next. Скрипт збірки читає його перед зміною дерева вихідних текстів і відмовляється працювати з неочікуваним комітом. Це запобігає застосуванню серії патчів до незафіксованої upstream-ревізії та робить оновлення невеликою зміною, придатною до перевірки, замість прихованої заміни архівом. Він не містить образів пристрою чи шляхів до інструментів.

## Усунення несправностей

### `ERROR: patch not found: susfs-v2.2.0-redbull.patch`

Звичайною причиною був кінець рядка CRLF у `patches/series`, через який Bash шукав файл з прихованим символом повернення каретки в кінці імені. Серія, що відстежується, тепер використовує LF, а скрипт збірки захисно видаляє завершальний символ повернення каретки.

```bash
cd "$PROJECT_DIR"
git status --short
file patches/series
test -f patches/susfs-v2.2.0-redbull.patch
```

### Скрипт збірки відмовляється працювати з брудним деревом вихідних текстів ядра

Це навмисно. Скрипт має починати з закріпленого коміту бази Google. Виконайте розділ 3, а потім повторіть спробу. Не обходьте цю перевірку, оскільки тоді доказ більше не визначатиме відтворюваний стан вихідних текстів.

### ABI-аудит повідомляє про розбіжність

Не пакуйте й не прошивайте. Збережіть звіт, визначте змінений експортований символ і скоригуйте патч сумісності KMI, не вилучаючи потрібну функцію SuSFS.

### Менеджер KernelSU та вбудований компонент показують різні номери

Зафіксуйте обидві версії та коміт вихідних текстів із доказу. Не змінюйте арифметику версії Kbuild лише для імітації номера менеджера; спочатку перевірте очікування для цього релізу KernelSU-Next.

## Історичні нотатки

Початкову несумісність спричинили змінені CRC експортованих символів у ядрі, тоді як стоковий `vendor.img` Pixel 5 зберіг модулі, зібрані зі стоковими CRC. Підхід KMI відновлює сумісність зі стоковими модулями без вилучення SuSFS. Успішний аудит раніше перевірив 111 стокових модулів vendor і не виявив CRC-розбіжностей або відсутніх символів ядра.
